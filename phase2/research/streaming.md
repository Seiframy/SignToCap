# Streaming validation notes

Verified 26 November 2026 from upstream code, papers and service documentation. No model, webcam, or vendor execution was performed for these notes.

## What the reference implementations support

- The Uni-Sign script named online inference takes a video file, reads it to completion, extracts its poses, creates a one-sample dataset, and prints one translation. It has no streaming input, state, caption events, or trained end-of-utterance detector. Benchmark it for clip parity, then reuse its pose and translation path inside a long-lived worker. [Uni-Sign online demo](https://github.com/ZechengLi19/Uni-Sign/blob/main/demo/online_inference.py)
- The vendored lightweight extractor is RTMW with YOLOX-Tiny. The demo uses BGR uint8 frames through OpenCV, ONNX Runtime, `lightweight`, and `to_openpose=False`. The worker input is one COCO-WholeBody person per frame, with `keypoints` shaped `[1, 133, 2]` and `scores` shaped `[1, 133]`. Divide x by the input frame width and y by its height exactly once. Keep landmarks in the capture orientation and mirror the preview only. Order and confidence are model inputs. Start with the same extractor for replay and live capture. [Wholebody configuration](https://github.com/ZechengLi19/Uni-Sign/blob/main/demo/rtmlib-main/rtmlib/tools/solution/wholebody.py) · [Pose extraction](https://github.com/ZechengLi19/Uni-Sign/blob/main/demo/pose_extraction.py) · [Uni-Sign dataset code](https://github.com/ZechengLi19/Uni-Sign/blob/main/datasets.py)
- The extractor can return a whole-frame pose even when YOLOX finds nobody. The model path blindly indexes person zero and masks scores at or below 0.3. Keep a consistent single-signer region, track the chosen person if a second detection appears, and report tracking loss separately from an observed pause. Test idle and ordinary non-sign motion because high confidence alone does not detect signing. [Pose wrapper](https://github.com/ZechengLi19/Uni-Sign/blob/main/demo/rtmlib-main/rtmlib/tools/pose_estimation/rtmpose.py) · [Uni-Sign keypoint normalization](https://github.com/ZechengLi19/Uni-Sign/blob/main/datasets.py#L16-L99)
- For parity, use a single sample via `S2T_Dataset_online(args)`, set `pose_data`, and use its `collate_fn` on that sample. Keep `rgb_support=False`. Bound input below `max_length` because the adapter randomly samples frames once over that setting. For warmed runs keep one eval-mode BF16 model and use `torch.inference_mode()`. The stock inference path computes training loss against an empty target then encodes again inside `generate`. If it misses cadence, expose the pose embeddings, English prompt embeddings and combined attention mask just above target tokenization, then call mT5 generation directly. Check generated token parity for fixed inputs and decoding settings before timing that optimization. [Dataset adapter](https://github.com/ZechengLi19/Uni-Sign/blob/main/datasets.py#L556-L616) · [Model and generation path](https://github.com/ZechengLi19/Uni-Sign/blob/main/models.py#L239-L295)
- ReSCUE is an architecture reference. Its public repository still has a placeholder README. Its trained streaming model sees prefixes, pauses with a learned silence token, and adjacent sentences. Appendix F explicitly describes proportional video and text truncation. The attached report juxtaposes ReSCUE with advice to avoid that heuristic. Use reviewed prefix targets or a boundary-only experiment because How2Sign notes that ASL and English timing can diverge. ReSCUE's published 1.58 s average lagging measures a different quantity from time to first useful on-screen caption. Its paper reports RTX 3090 inference-step timings separately. [ReSCUE paper, sections 3 and appendices F/G](https://arxiv.org/html/2610.03022v1) · [Release status](https://github.com/Tabiiiqwq/ReSCUE) · [How2Sign](https://how2sign.github.io/)
- StreamSLST releases code for learned joint localization and translation on windows. Authors report that real-time inference optimization is future work. BCP evaluates a frozen translator plus a small boundary adapter supervised by CTC alignments from an existing sign recognizer on German PHOENIX-2014T and Chinese CSL-Daily. It supplies a training idea for ASL, with ASL supervision and meeting validation still required. [StreamSLST repository](https://github.com/streamsl/StreamSLST) · [StreamSLST paper](https://arxiv.org/html/2611.00055v1) · [BCP paper](https://arxiv.org/abs/2611.32471)

## Capture, transport and caption state

1. Start with prerecorded replay and one signer. Run the vendored pose extractor on the cloud GPU for replay. For live capture prefer the same extractor on the laptop once its CPU can meet the chosen cadence and maintain acceptable tracking. Start with 25–30 fps replay at its native uniform cadence, and test any lower pose cadence against the same clips and reference timings. If laptop throughput fails, explicitly opt in to raw video for cloud pose extraction using the same extractor. Record this as a separate benchmark condition.
2. Send one small batch every 500 ms over an authenticated TLS WebSocket. On connect negotiate `coco-wholebody133-v1`, frame rate and session ID. Each batch carries a monotonic sequence number, client-relative frame timestamps, and one `[133, 3]` x/y/score vector per frame. Use float32 binary if the JSON proof adds measurable overhead. Landmark payload alone is about 48 kB/s at 30 fps in float32. Use a one-signer quality flag or zeroed scores for missing frames. Poses stay in a short in-memory session buffer.
3. Keep up to 8 seconds of uncommitted pose frames for the first experiment, with 4 and 12 seconds as development comparisons if there is room under the model frame cap. Wait for about 1 second of usable pose at the start of a segment. Schedule at most one model decode in flight. If the worker is busy, coalesce pending requests to the latest window and count skipped updates. Reject stale results by session, segment generation and input watermark. On long gaps or reconnect start a fresh segment and clear provisional text. Preserve already finalized lines locally.
4. Translate each snapshot from scratch. Keep the last three hypotheses in the active segment. Use the longest common word prefix across the last two hypotheses to reduce visible edit churn, and allow revisions until finalization. Use the last three when assessing a stable ending, and only compare updates that consumed new frames. Repeated outputs from identical evidence do not establish stability.
5. Commit when a stable, meaningful hypothesis coincides with an observed likely boundary, initially about 600–800 ms of low signing activity while the signer remains trackable. Use a healthy same-signer observation and body-normalized hand motion as weak cues, because holds, facial grammar and between-sign motion may look like pauses. Detect early stable punctuation as an experimental second policy for no-pause streams. Estimate its source cut from the first input watermark where the punctuation appeared and survived later hypotheses, preserve frames after that watermark, and log it as a heuristic boundary. Keep the pause-only and punctuation-assisted outputs separately scored. On pause use the last active frame as the source-end estimate. Decode pending content once on end-of-input. At an 8 s cap without a reliable boundary, clear stale context as needed and report an uncertain segment, missed/forced boundary and discarded duration. Do not silently promote unstable text to a final caption.
6. Emit `partial` and immutable `final` caption events with session ID, monotonic event sequence, segment ID, revision, source start/end estimates, and text. Emit status for camera loss, missing packets, overrun, and reconnect. Replace the active partial in the Tauri/Rust state and append finals by segment ID. Treat video shown to meeting participants as a separate output leg. A later test can share a captioned preview window or layer a local caption source into an OBS scene and use OBS Virtual Camera. Use one physical camera owner and distribute its preview frames to display and pose extraction. [OBS Browser Source](https://obsproject.com/kb/browser-source) · [OBS Virtual Camera](https://obsproject.com/kb/virtual-camera-guide)

## Experiment order and interpretation

| Arm | Input | What a failure isolates |
| --- | --- | --- |
| 1 | Official pose samples or compatible prerecorded How2Sign clips with known boundaries | Checkpoint, paths, pose compatibility and decoding |
| 2 | Meeting-like webcam clips with human-marked boundaries | Webcam pose quality or domain mismatch if Arm 1 passes |
| 3 | Real-time replay of the same multi-utterance webcam clips without boundaries | Incremental evidence, boundary policy and overrun if Arm 2 passes |
| 4 | Live webcam via actual WebSocket and rendered text | Capture throughput, transport and end-to-end delay |

Use at least three consenting ASL signers if available and set aside whole clips and at least one signer for the untouched evaluation. Include several uninterrupted runs, inter-utterance pauses, within-utterance holds, idle and non-sign movement, hands near frame edges, and meeting-domain details like numbers, dates and negation. Keep a fixed set of clips for each comparison. Capture benchmark-only metrics without retaining webcam video or pose payloads by default.

- Have an ASL-fluent reviewer mark sign onset, sign end, whether a partial conveys a correct complete idea, and meaning preservation of the final. Score important substitutions such as wrong negation, dates, amounts, names and role assignment. A missing first useful or final caption is a miss, not a zero or excluded success.
- First useful latency is the time from annotated onset to first rendered partial with a correct meaningful unit. Final latency is time from annotated end to rendered final. Count premature finals independently, including merged and split clauses. Report median and p95 with sample counts and miss counts. Keep client capture and display timestamps on one monotonic clock. Time GPU stages locally and round-trip transport at the client to avoid clock skew.
- Report pose effective FPS and tracking loss, model warm p50/p95 with synchronized GPU timing, queue delay and pending decode drops, peak Torch allocated/reserved bytes and device total including ONNX. Compute model update occupancy as wall-clock decode time divided by scheduled tick and report total real-time processing factor separately.
- Count non-append changes by erased words, how often the stable prefix changes, and any final changes. Also count hallucinated idle finals/minute, lost or duplicated clauses, and overflow or reset events. Keep any tuning thresholds fixed for the held-out run.
- If aligned full clips fail, test pose parity and domain quality before optimizing captions. If aligned full clips pass but automatic boundaries fail, first compare fixed pause/commit policies. A remaining failure warrants a tiny boundary head while keeping the translator frozen. Use manually realigned source boundaries or reviewed continuous webcam segments, keep true pause and within-utterance hold negatives, and split by source video. If even oracle-cut prefixes are semantically unreliable, treat reliable phrase-level finals as a fallback. Any prefix translator training would need reviewed alignment targets and a separate decision.
- If compute misses cadence, first eliminate the duplicate encoder call, use BF16 and compare warm greedy/beam-2 and shorter output caps against clip-level beam-4 quality. Cache extracted poses and invariant prompt embeddings. Window-wide pose normalization and bidirectional mT5 source attention can change with every frame, so cross-window encoder or decoder KV reuse requires new correctness evidence. Consider an ONNX/export or quantization trial only against a measured bottleneck and after a quality parity check.

## Vendor fallback

Sign-Speak publicly documents a real-time JavaScript WebSocket SDK with 500 ms video slices and references WebRTC as its preferred real-time option. The WebRTC documentation link did not open in this check. Streaming authentication, the exact partial/final contract, service latency, rates, and data terms need validation before sending live video. Map vendor outputs through the same caption event interface and benchmark the same held-out clips. The vendor requires video input for this path, so use an opt-in test and keep private credentials server-side. Its public translation page does not provide enough benchmark protocol to compare its headline BLEU with the How2Sign results. If access is unavailable and Uni-Sign passes the oracle arm, use explicit signer-controlled segments as a fallback for live captions.
